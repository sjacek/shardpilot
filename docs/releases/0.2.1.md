# ShardPilot 0.2.1

[Release guide](../releases.md) · [Changelog](../../CHANGELOG.md)

Status: **publication pending**. Project version: `0.2.1`. Release tag: `v0.2.1`.
This candidate supersedes the unpublished 0.2.0 candidate and includes the expanded Plugin Portal
description. The existing `v0.2.0` tag remains unchanged. Rerunning its workflow would still use
the old description; publish the new commit through `v0.2.1` instead.

## Purpose and changes

ShardPilot helps shorten CI feedback for large JVM unit and integration test suites by splitting
Gradle test tasks into deterministic, non-overlapping class-level shards for parallel CI jobs.
Historical durations balance the workload; deterministic hashing handles classes without timing data.
Existing JUnit Jupiter, Spock and TestNG tasks, filters and nested test families are preserved.
Optional process settings configure worker heap size, parallel forks and process recycling.
Configuration Cache and CI-provider independence remain supported; CI launches every shard and
collects the results.

The project description in `build.gradle` is the source for both the Plugin Portal description
and Maven metadata. Version 0.2.1 changes release metadata and documentation, with no runtime
changes relative to the 0.2.0 candidate. It includes all of that candidate's optional `testProcesses`
API; see the [configuration examples](../../README.md#optional-test-process-settings).

After Portal publication, consumers can apply:

```groovy
plugins {
    id 'io.github.sjacek.shardpilot' version '0.2.1'
}
```

Or Kotlin DSL:

```kotlin
plugins {
    id("io.github.sjacek.shardpilot") version "0.2.1"
}
```

Existing 0.1.0 sharding configuration needs no migration. Process settings are optional and retain
native task settings when omitted. Per-JVM heap limits are not a complete runner memory budget
and do not guarantee that every test fits its heap.

## Verification and publication

The unchanged runtime implementation passed all eight Gradle/JDK combinations in the 0.2.0
candidate matrix. The new tag workflow reruns all eight combinations at the exact 0.2.1 release
commit before publishing; prior green results do not replace that gate.

1. Ensure the GitHub environment `gradle-plugin-portal` contains `GRADLE_PUBLISH_KEY` and
   `GRADLE_PUBLISH_SECRET`; see the [environment setup](../releases.md#configure-github-publication).
2. From the ShardPilot repository root, select Temurin 25 and run:

   ```powershell
   .\gradlew.bat verifyReleaseTag '-PreleaseTag=v0.2.1' check assemble
   .\gradlew.bat publishPlugins --validate-only --no-configuration-cache --no-daemon
   git diff --check
   git diff --cached --check
   ```

3. Review the release changes, then execute these commands yourself:

   ```powershell
   git add build.gradle README.md CHANGELOG.md docs
   git diff --cached
   git commit -m "Release ShardPilot 0.2.1 with expanded Plugin Portal description"
   git push origin HEAD
   git tag -a v0.2.1 -m "ShardPilot 0.2.1"
   git push origin refs/tags/v0.2.1
   ```

   The new tag must point to the commit containing both `version = 0.2.1` and the expanded
   description. Commits and pushes are performed by the maintainer.
4. Follow **Actions → Publish Gradle plugin**: version guard → complete compatibility matrix →
   Portal validation → publication. Approve the environment if its protection rules require it.
5. Check the [0.2.1 Portal page](https://plugins.gradle.org/plugin/io.github.sjacek.shardpilot/0.2.1)
   and run the isolated consumer check below. The workflow does not create a GitHub Release.
6. Once Portal resolution succeeds, record the actual Portal creation date in the changelog,
   update the README/documentation status and installation snippets to 0.2.1, and create a GitHub
   Release from these notes if desired. Tichodroma already pins `shardPilotVersion=0.2.1`; normal
   builds can resolve it after publication without a local included build.

## Verify Portal resolution after publication

This creates a separate consumer with a fresh Gradle user home and no local plugin substitution.
Its empty `test` task verifies published plugin resolution and the process-configuration DSL;
actual test execution is covered by TestKit in the compatibility matrix.

```powershell
$releaseSmoke = Join-Path ([IO.Path]::GetTempPath()) ("shardpilot-0.2.1-" + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $releaseSmoke | Out-Null
@'
pluginManagement {
    repositories { gradlePluginPortal() }
}
rootProject.name = 'shardpilot-portal-smoke'
'@ | Set-Content -LiteralPath (Join-Path $releaseSmoke 'settings.gradle') -Encoding utf8
@'
plugins {
    id 'java'
    id 'io.github.sjacek.shardpilot' version '0.2.1'
}
tasks.named('test', Test) {
    shardPilot {
        testProcesses {
            maxHeapSize = '256m'
            maxParallelForks = 1
            forkEvery = 2L
        }
    }
}
'@ | Set-Content -LiteralPath (Join-Path $releaseSmoke 'build.gradle') -Encoding utf8
.\gradlew.bat -p $releaseSmoke -g (Join-Path $releaseSmoke 'gradle-user-home') test --refresh-dependencies --no-configuration-cache
if ($LASTEXITCODE -ne 0) { throw 'ShardPilot 0.2.1 Portal resolution failed.' }
```
