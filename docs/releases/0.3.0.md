# ShardPilot 0.3.0

[Release guide](../releases.md) · [Changelog](../../CHANGELOG.md)

Project version: `0.3.0`. Release tag: `v0.3.0`.

This release adds opt-in `shardPilot.verification` for class-candidate manifests and cross-job
coverage gates, standalone HTML reports and a Maven Surefire/Failsafe adapter. Existing Gradle
sharding and `testProcesses` consumers need no configuration migration.
The plugin still targets Java 17 bytecode; the compatibility matrix must pass at the release revision.

Sources now live in sibling `shardpilot-core`, `shardpilot-gradle-plugin` and
`shardpilot-maven-plugin` modules. The Gradle adapter retains its plugin ID, Java API/DSL, tasks,
marker and implementation coordinates; its distribution JAR bundles the core. Root included-build
consumption remains valid. Gradle examples moved to `examples/gradle`; Maven examples live under
`examples/maven`. [The Maven guide](../maven.md) covers native Surefire/Failsafe setup, goal phases,
supported filters and deliberate rejection of overrides that could bypass shard ownership.

For local Maven development, `./mvnw -B -ntp install -DskipITs` installs the parent, core and
Maven adapter into the local repository. Bind `select` before the native runner and explicitly
request `prepare`/`verify` for artifact planning/aggregation. `mvn verify` remains the native
lifecycle/result gate; `mvn shardpilot:verify` is only the selection gate. See the
[adapter configuration map](../configuration.md#gradle-and-maven-configuration-map) and
[Maven CI sequence](../ci.md#maven-ci-sequence). Gradle process controls are not Maven parameters.

Consumers using a repository-root Gradle composite keep their existing `includeBuild` path.
Maintainer scripts pointing at the old root `build/libs` or `build/reports/tests/test` must use
the new [module output paths](../testing.md#local-verification). Source/package/API names remain
stable, but internal repository paths are now module-specific.

See the [API and CI sequence](../../README.md#optional-class-manifest-verification). Preparation
and execution use the same planner and history. Consumers explicitly supply their unsharded
eligible bytecode tree and retain responsibility for test discovery, all CI nodes and JUnit outcomes.

The [manifest guide](../shard-verification.md) documents the configuration reference, task/CI/validation
diagrams and failure boundaries. Files are now YAML with `schemaVersion: 1` and a `classes` string
sequence, named `baseline.yaml`, `planned-N.yaml` and `actual-N.yaml`. Regenerate all artifacts
together when moving from the earlier text-format implementation. SnakeYAML Engine is resolved as
a Gradle-plugin runtime dependency and is not added to application/test worker classpaths.

Preparation and actual writing can reuse exact-input cached results; verification always inspects
current downloads. A failed test still leaves its actual selection, but successful selection coverage
does not convert that failed test into a pass. CI requires every test result and the coverage gate.

Verification also writes standalone `coverage.html` from the same evidence as `coverage.json`,
including class assignments, per-shard counts and diagnostics on failure. Configure `htmlReportFile`
to move it independently of JSON. The [GitLab publisher example](../shard-verification.md#finding-a-class-assignment-in-gitlab)
exposes a direct merge-request artifact link without credentials or scripts in the report.

Both report paths are independent of each other and the manifest directories. Consumers overriding
`reportFile` must also set `htmlReportFile` when they want to relocate HTML; update both CI artifact
paths. See [Groovy/Kotlin output examples](../configuration.md#json-and-html-report-paths) and the
[status reference](../shard-verification.md#reading-html-statuses). `PASSED` in plan-only mode does
not establish actual node selection, and matching HTML rows do not override a failed global gate.

For GitLab, retain both formats in verification and expose only HTML from a lightweight publisher
when a direct MR file link is desired. Schedule the two jobs and artifact uploads after failures,
align their inclusion rules and confirm Pages/access-control preview behavior on the instance.
No GitLab client, token, web server or report JavaScript is added to the plugin.

`tichodroma-svc` requires this API and pins `shardPilotVersion=0.3.0`. Verify before publication with
its explicit local override `-PshardPilotBuildDir=../gradle-plugins/shardpilot`. Do not deploy that
override to CI or restore a copied implementation in the service. Publish 0.3.0 before running
the ordinary service pipeline against Plugin Portal resolution.

Before release, run `check assemble verifyReleaseTag -PreleaseTag=v0.3.0` and the tag workflow's
full compatibility matrix, plus `./mvnw -B -ntp verify` for the native Maven reactor. The reusable
gate includes Maven 3.9.16/JDK 17, 21 and 25 and a credential-free signed-bundle check. The tag
workflow publishes Gradle on tag push; a later manual run from the same tag reruns the gate and
publishes only Maven Central. The Maven job signs the parent/core/adapter cohort, including sources and Javadoc, and waits for
Central publication. See [Central setup](../maven-central.md) and [release distribution boundaries](../releases.md).
Publication, tags, commits and pushes remain maintainer actions;
this change does not publish artifacts or claim that local verification replaces the matrix.
