## Choose tests through configuration

Choose a full suite, a small mandatory smoke suite, affected tests or an explicit subset
using the same YAML policy in Gradle and Maven. Committed Git changes, directly changed
tests, declared module dependencies and JSON/YAML contract rules can select tests without
an application-specific selector. Required tests stay protected when applying size and
estimated-time budgets. Unknown ownership or unavailable changes follow an explicit full
run or failure policy. Decisions explain selection, deferral and fallback.

Freeze one decision for all parallel workers. Its policy, history, eligibility, profile,
revision and shard count remain bound together; mismatched workers fail validation.
See [profiles and Git parameters](../selection-policy.md) and [impact rules](../selection-impact.md).

## Check the compiled inputs and native results

Seal compiled classes/resources with SHA-256 and the expected source revision, then check
transferred files before tests. Missing, changed, extra or wrong-revision inputs stop workers.
Bind the selection decision and optional compilation manifest to execution evidence.
JSON/HTML reports expose missing native reports, failed processes, mixed cohorts and
unexpected skips; matching class plans alone do not prove successful execution.

See [compiled inputs](../compiled-artifacts.md), [execution evidence](../execution-evidence-contract.md)
and [selection binding](../execution-selection.md). Optional
[execution diagnostics](../execution-diagnostics.md) describe memory use, timeouts,
interruptions and leftover containers. Detection does not delete containers.

## Upgrade from 0.5.0

Set the Gradle plugin to `0.6.0` or Maven coordinates to
`io.github.sjacek:shardpilot-maven-plugin:0.6.0`. The examples also document explicit
source-development configuration for contributors.

- Existing explicit class manifests and v1 execution/node/compiled-artifact formats remain supported.
  Selection-to-evidence binding uses its separate v2 envelope.
- Profiles and diagnostics are opt-in. Supply independent full native eligibility; do not
  substitute the selected subset for the baseline.
- Git input is committed history. Fetching remains opt-in; working-tree impact is not inferred.
- Every worker needs the same plugin version, policy, frozen selection, history and count.
  Keep native failure gates and dedicated/module suites independently owned.
- Use a separately supplied expected revision and compilation-manifest digest. A digest
  downloaded beside mutable files is not independent authentication.
- Configure Maven's native Surefire/Failsafe exclusions and report locations as shown in the
  examples. The plugin does not schedule CI jobs or replace native test runners.

The supported build/JDK matrix and Java 17 bytecode target are unchanged. No dependency or
Wrapper update is part of the 0.6.0 release preparation.

## Runnable acceptance and examples

The matching [Gradle](https://github.com/sjacek/shardpilot/blob/main/examples/gradle/junit-jupiter/selection-workflow/README.md)
and [Maven](https://github.com/sjacek/shardpilot/blob/main/examples/maven/selection-workflow/README.md)
examples exercise smoke, full and affected profiles through planning, compilation sealing,
two native workers and artifact-only aggregation. The release-acceptance affected profile
maps an actual committed Git diff to one required boundary probe; its broad rule is a test
fixture, not a production ownership policy.

Fresh-consumer acceptance resolves the actual marker/POM/module/JAR files in a disposable
repository. It has no source substitution and excludes cached ShardPilot binaries. Strict
native verification pins binary, metadata, sources and Javadoc artifacts. Both tools must
reject changed compiled bytes and a wrong revision before native test reports appear.

Candidate receipts identify a locally built package cohort. Registry-mode acceptance requires
a completed signature/source/isolation audit of the same version before importing its bytes.
An unpublished candidate pass does not establish Plugin Portal or Maven Central availability.
