# ShardPilot 0.2.0

[Release guide](../releases.md) · [Changelog](../../CHANGELOG.md)

Status: **publication pending**. Project version: `0.2.0`. Release tag: `v0.2.0`.
These notes can be used for the GitHub Release after Portal publication succeeds.

## Changes

Optional per-task `shardPilot.testProcesses` settings configure Gradle's existing worker JVMs:

| Property | Meaning | Accepted values |
| --- | --- | --- |
| `maxHeapSize` | Maximum heap per test JVM. | Positive byte count or JVM size such as `512m` or `2g`. |
| `maxParallelForks` | Maximum simultaneous test processes for the task. | Positive integer. |
| `forkEvery` | Classes per process before replacement between classes. | Nonnegative long; `0L` disables periodic replacement. |

The block works independently of sharding. Omitted settings preserve the existing task values.
Values can come from Gradle providers, are validated during configuration and participate in task
cache inputs. Configuration Cache remains supported. There are no changes to class assignment,
framework selection, retry behavior or failure propagation.

## Upgrade from 0.1.0

After 0.2.0 becomes available in the Plugin Portal, update the plugin version:

```groovy
plugins {
    id 'io.github.sjacek.shardpilot' version '0.2.0'
}
```

Existing sharding configuration needs no migration. Existing native Gradle process settings can
stay as they are. To opt into the new API, move only the desired values into the block, preserving
your current limits and provider defaults. For an already registered `integrationTest` task:

```groovy
tasks.named('integrationTest', Test) {
    shardPilot {
        testProcesses {
            maxHeapSize = providers.gradleProperty('testHeap').orElse('2g')
            maxParallelForks = 1
            forkEvery = 50L
        }
    }
}
```

Kotlin DSL:

```kotlin
import io.github.sjacek.shardpilot.ShardPilotExtension

plugins {
    id("io.github.sjacek.shardpilot") version "0.2.0"
}

tasks.named<Test>("integrationTest") {
    extensions.configure<ShardPilotExtension>("shardPilot") {
        testProcesses {
            maxHeapSize.set(providers.gradleProperty("testHeap").orElse("2g"))
            maxParallelForks.set(1)
            forkEvery.set(50L)
        }
    }
}
```

These values are examples, not new defaults. Providers are read when the block completes; later
native `Test` assignments follow normal Gradle configuration order. A heap limit applies per JVM
and does not include native memory, Gradle daemons or containers. Recycling processes cannot
prevent an individual test class from exceeding its heap. Framework threads and CI resource
allocation remain the consumer's responsibility.

## Publish this version

1. Configure the GitHub environment `gradle-plugin-portal` with `GRADLE_PUBLISH_KEY` and
   `GRADLE_PUBLISH_SECRET` as described in the [release setup](../releases.md#configure-github-publication).
2. From the repository root, using a supported JDK (the publishing workflow uses Temurin 25), run:

   ```powershell
   .\gradlew.bat verifyReleaseTag '-PreleaseTag=v0.2.0' check assemble
   git diff --check
   git diff --cached --check
   git status --short
   ```

3. Review the release diff, then commit and push it yourself. Verify that the intended commit is
   on GitHub before tagging it. The following commands are for the maintainer to execute:

   ```powershell
   git add --all
   git diff --cached
   git commit -m "Release ShardPilot 0.2.0"
   git push origin HEAD
   git tag -a v0.2.0 -m "ShardPilot 0.2.0"
   git push origin refs/tags/v0.2.0
   ```

   Push the tag once, on the reviewed release commit. Do not move or recreate a published tag.
4. Follow **Actions → Publish Gradle plugin**: version guard → eight-cell matrix → Portal
   validation → publication. Approve the environment if its protection rules require it.
5. Confirm the [0.2.0 Portal page](https://plugins.gradle.org/plugin/io.github.sjacek.shardpilot/0.2.0)
   is available, then run the isolated resolution check below. The workflow does not create a
   GitHub Release; create one from these notes if desired.
6. After Portal resolution succeeds, mark 0.2.0 as published in the changelog with the actual
   Portal date, and update the README/documentation status and installation snippets to 0.2.0.

## Verify Portal resolution after publication

Run this from the ShardPilot repository root. It creates a separate consumer and a fresh Gradle
user home, resolves only from the Plugin Portal and realizes the new DSL on the standard `test`
task. It deliberately has no test sources: this checks published resolution/configuration; the
TestKit matrix covers actual test execution.

```powershell
$releaseSmoke = Join-Path ([IO.Path]::GetTempPath()) ("shardpilot-0.2.0-" + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $releaseSmoke | Out-Null
@'
pluginManagement {
    repositories { gradlePluginPortal() }
}
rootProject.name = 'shardpilot-portal-smoke'
'@ | Set-Content -LiteralPath (Join-Path $releaseSmoke 'settings.gradle') -Encoding utf8
@'
plugins {
    id 'java'
    id 'io.github.sjacek.shardpilot' version '0.2.0'
}
tasks.named('test', Test) {
    shardPilot {
        testProcesses {
            maxHeapSize = '256m'
            maxParallelForks = 1
            forkEvery = 2L
        }
    }
}
'@ | Set-Content -LiteralPath (Join-Path $releaseSmoke 'build.gradle') -Encoding utf8
.\gradlew.bat -p $releaseSmoke -g (Join-Path $releaseSmoke 'gradle-user-home') test --refresh-dependencies --no-configuration-cache
if ($LASTEXITCODE -ne 0) { throw 'ShardPilot 0.2.0 Portal resolution failed.' }
```

Do not add `includeBuild`, `mavenLocal()` or an init script substituting a local plugin. A
successful local composite build is not evidence that the Portal release can be resolved.
