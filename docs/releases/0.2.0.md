## Changes

Optional per-task `shardPilot.testProcesses` settings configure Gradle's existing worker JVMs:

| Property | Meaning | Accepted values |
| --- | --- | --- |
| `maxHeapSize` | Maximum heap per test JVM. | Positive byte count or JVM size such as `512m` or `2g`. |
| `maxParallelForks` | Maximum simultaneous test processes for the task. | Positive integer. |
| `forkEvery` | Classes per process before replacement between classes. | Nonnegative long; `0L` disables periodic replacement. |

The block works independently of sharding. Omitted settings preserve the existing task values.
Values can come from Gradle providers, are validated during configuration and participate in task
cache inputs. Configuration Cache remains supported. There are no changes to class assignment,
framework selection, retry behavior or failure propagation.

## Upgrade from 0.1.0

After 0.2.0 becomes available in the Plugin Portal, update the plugin version:

```groovy
plugins {
    id 'io.github.sjacek.shardpilot' version '0.2.0'
}
```

Existing sharding configuration needs no migration. Existing native Gradle process settings can
stay as they are. To opt into the new API, move only the desired values into the block, preserving
your current limits and provider defaults. For an already registered `integrationTest` task:

```groovy
tasks.named('integrationTest', Test) {
    shardPilot {
        testProcesses {
            maxHeapSize = providers.gradleProperty('testHeap').orElse('2g')
            maxParallelForks = 1
            forkEvery = 50L
        }
    }
}
```

Kotlin DSL:

```kotlin
import io.github.sjacek.shardpilot.ShardPilotExtension

plugins {
    id("io.github.sjacek.shardpilot") version "0.2.0"
}

tasks.named<Test>("integrationTest") {
    extensions.configure<ShardPilotExtension>("shardPilot") {
        testProcesses {
            maxHeapSize.set(providers.gradleProperty("testHeap").orElse("2g"))
            maxParallelForks.set(1)
            forkEvery.set(50L)
        }
    }
}
```

These values are examples, not new defaults. Providers are read when the block completes; later
native `Test` assignments follow normal Gradle configuration order. A heap limit applies per JVM
and does not include native memory, Gradle daemons or containers. Recycling processes cannot
prevent an individual test class from exceeding its heap. Framework threads and CI resource
allocation remain the consumer's responsibility.

amd64 in official Eclipse Temurin containers:

| Consumer Gradle | JDK 17 | JDK 21 | JDK 25 |
| --- | --- | --- | --- |
| 9.0.0 | PASS | PASS | Outside the matrix |
| 9.1.0 | PASS | PASS | PASS |

Every pair ran `check assemble`: 67 tests per pair, 536 executions, zero failures or skips.
Coverage includes actual Gradle/JDK runtime assertions, real heap/process/replacement probes,
strict Configuration Cache reuse, Groovy/Kotlin DSL, JUnit Jupiter, Spock and TestNG.
The matrix did not run the separate Docker-backed Testcontainers examples.
Release documentation was finalized after that run; the tag workflow reruns the full matrix on
the exact release commit before uploading. See [testing scope](../testing.md).

`verifyReleaseTag -PreleaseTag=v0.2.0`, publication POM/module generation and
`publishPlugins --validate-only --no-configuration-cache --no-daemon`. The three JARs contain
the MIT license, the main JAR has the correct plugin descriptor and Java 17 bytecode, and the
marker POM points to `io.github.sjacek:shardpilot:0.2.0`. No artifacts were published.
